## 三、插件系统深度分析与 v2 设计

### 3.1 现状（src/lib/plugins.ts，188 行）

合同 `I18nPlugin` 七钩子：`init / destroy / beforeTranslate / afterTranslate / onLocaleChange / onError / onMissingKey`；内置三插件：console-logger、missing-key-reporter（含 autoExport）、performance-tracker（含 slow 阈值与分位统计）。

### 3.2 五项痛点（实查定位）

| # | 痛点 | 证据 | v2 方案 |
| ---- | ---- | ---- | ---- |
| P1 | 钩子**无优先级**——`hookOrder` 即注册序，多插件协作顺序不可控 | plugins.ts:55 `hookOrder: string[]` | `register(plugin, { priority })`，钩子按 priority 稳定排序 |
| P2 | 钩子**类型不对称**——beforeTranslate 返回 `{key,params}｜void`，afterTranslate 返回 `string｜void`，管线语义不一致 | plugins.ts:44-45 | 统一 `PipelineResult<T>`，中间件链签名 `ctx → next()` 化 |
| P3 | **无插件发现机制**——PluginManager 单实例强耦合引擎，无约定目录/懒加载（对比 locale registry 已有 LAZY_LOCALE_REGISTRY 先例） | registry.ts 模式可复制 | `plugins/registry.ts`：`loadPlugin(name)` 懒加载 + 包内 `plugins/` 约定目录 |
| P4 | **单向通信**——onLocaleChange 仅引擎→插件，插件间无事件总线 | plugins.ts:48 | 引擎级 `eventBus`（emit/on），插件可发布 `i18n:report` 类事件 |
| P5 | **内置面薄**——仅日志/缺失上报/性能三项 | plugins/index.ts 39 行 | 新增：cache-warmer（预热高频键）、glossary（术语强制）、tm（翻译记忆）、watcher（键脏检查） |

### 3.3 插件合同 v2（提案骨架）

```typescript
export type I18nPluginV2 = I18nPlugin & {
  priority?: number;                       // P1：默认 100，小者先执行
  meta?: { capability: string[] };         // P3：能力声明（供技能/MCP 发现）
  eventBus?: { emit(topic: string, payload: unknown): void;   // P4
               on(topic: string, h: (p: unknown) => void): () => void };
};
```

向后兼容承诺：v2 为 v1 纯超集，`register(v1Plugin)` 零改动可用（3.1.x 用户无损升级）。

## 四、MCP 现状分析与 G2 扩张设计

### 4.1 现状（src/lib/mcp/，797 行）

工具面 5 个：`search_translations / add_translation_key / translate_key / check_missing_keys / get_locale_stats`；传输仅 `StdioTransport`；仅用 MCP 三原语中的 Tools（Resources/Prompts 未用）。

**文档漂移发现**：趋势文档 Phase 3 节记载的现存 5 工具名（translate_batch/detect_language/validate_icu/audit_coverage/suggest_keys）与实况不符——演进时**以实为准**并回写趋势文档（G1 文档漂移门禁的动机之一）。

### 4.2 G2 工具面扩张（5→12），每一项都是既有模块的协议化

| 新工具 | 复用模块 | 说明 |
| ---- | ---- | ---- |
| extract_keys | cli-integration `extractKeys` 正则逻辑移植 TS | 从代码文本提取 t() 键（MCP 输入=文件内容而非 glob，规避沙箱文件系统暴露） |
| compare_locales | auditCoverage 扁平化逻辑 | 双语言键差异矩阵 |
| quality_score | ai/quality-estimator | 翻译质量评分 |
| auto_fix_icu | icu/parser errors + compiler | ICU 错误定位与安全修复建议 |
| export_formats | 新增 serializer | JSON/YAML/XLIFF/CSV 导出 |
| glossary_lookup | 新增 glossary 模块（G3 插件同源） | 术语强制查询 |
| （升级）report_missing / get_perf | missing-key-reporter / performance-tracker | 内置插件能力 → MCP 工具（G3 三位一体前置） |

### 4.3 传输矩阵与资源面（v1.1.0 按行业标规修正）

- **Streamable HTTP Transport**（MCP 规范 2025-03-26 起的现行标准，已取代 HTTP+SSE 双端点旧设计）：**单一 MCP 端点**接收全部 POST 消息，响应可选 SSE 流式——本仓以 `node:http` 原生自实现（零依赖红线，社区已有 ~500 行零依赖实现先例可参考）；**WebSocket 非官方传输**（仅社区提案），不纳入主线，仅在插件层留第三方扩展点
- ~~SSE Transport + WebSocket Transport~~（v1.0.0 原案，基于已废弃的 HTTP+SSE 双端点旧规范，修正如上）
- **Resources 面**：`locales://{locale}` URI 模板只读资源、`coverage://report` 订阅——符合官方 Resources 原语（URI Templates 支持）
- **结构重构**：i18n-tools.ts 277 行单文件拆为 tool-registry 模式（每工具一文件 + 各自测试），与插件注册表（P3）同构

## 五、插件 × MCP × 技能：三位一体设计（G3 核心）

### 5.1 三层映射

```
能力层（src/lib/plugins/ + ai/ + icu/）      ——运行时扩展点
    ↕ 一比一暴露
协议层（MCP Tools + Resources）              ——AI 工具机器可调用入口
    ↕ 一比一描述
认知层（skills/*/SKILL.md）                  ——AI 编程工具「何时/如何用」的说明书
```

**技能 = 能力的可发现描述 + 可执行入口**；同一实现，三种暴露面，单一事实源（与 YYC3-CLI 的 file: 单源模式同构）。

### 5.2 首批技能矩阵（6 个）

| 技能 | 触发场景 | 执行入口（指向单一事实源） |
| ---- | ---- | ---- |
| i18n-extract | 「给这段代码提取翻译键」 | MCP `extract_keys` 或 `yyc3 i18n extract` |
| i18n-audit | 「检查翻译覆盖率/缺失键」 | MCP `check_missing_keys` + `compare_locales` 或 `yyc3 i18n audit` |
| i18n-translate | 「把 en.json 翻成 ja」 | MCP `translate_key`（AI Provider 直通） |
| i18n-quality | 「评估翻译质量」 | MCP `quality_score` |
| i18n-icu | 「修复这条 ICU 报错」 | MCP `auto_fix_icu` |
| i18n-setup | 「给项目接入 i18n」 | `yyc3 i18n init` |

### 5.3 技能包规范（v1.1.0 对齐 Agent Skills 开放标准）

SKILL.md 已是开放标准（agentskills.io，兼容 Claude Code / Codex / Cursor / Amp / VS Code）。本仓技能包**双 front matter 融合**：开放规范必填字段 + YYC³ 标头标尾字段作为扩展保留。

```
skills/i18n-audit/
├── SKILL.md          # 开放规范 front matter（name+description 必填）+ YYC³ 扩展字段
└── scripts/          # 可执行脚本优先于长流程描述（标准最佳实践）
    └── audit.mjs     # 薄封装：调 @yyc3/i18n-core/mcp 或 yyc3 i18n audit
```

**front matter 合同**（字段顺序=开放规范优先，YYC³ 扩展随后）：

```yaml
---
name: i18n-audit                    # 必填·ASCII kebab-case（激活路由标识，禁止 YYC³ 上标字符）
description: >-                     # 必填·驱动激活匹配（何时用+能力一句话）
  Check i18n translation coverage and missing keys across locales.
  Use when auditing locale files or before i18n releases.
version: v1.0.0                     # ── 以下为 YYC³ 标头标尾扩展字段 ──
author: YYC³ Team <admin@0379.email>
category: skill
language: zh-CN
tags: [skill, i18n, audit]
---
```

**渐进披露三级纪律**（标准要求）：

| 层级 | 内容 | 预算 |
| ---- | ---- | ---- |
| L1 元数据 | name + description 常驻上下文 | ~100 tokens |
| L2 正文 | SKILL.md 激活时加载 | **< 5000 tokens** |
| L3 资源 | scripts/ 与参考文档按需读取 | 不限额 |

**提示词六要素 → SKILL.md 写作映射**（生成式 AI 提示词核心要素的行业共识：角色/上下文/任务/约束/输出格式/示例）：

| 提示词要素 | SKILL.md 落位 |
| ---- | ---- |
| 角色 Role | 正文首节：「你是 i18n 审计助手，遵循 @yyc3/i18n-core 约定」 |
| 上下文 Context | description 字段 + 正文「前置条件」节（引擎版本/语言清单） |
| 任务 Task | 正文「工作流」节（编号步骤，每步指向脚本或 MCP 工具） |
| 约束 Constraints | 正文「红线」节（键名规范/不得直改 locale 文件/CI 门禁链接） |
| 输出格式 Format | 正文「报告格式」节（对齐 yyc3 i18n audit 的 JSON 报告结构） |
| 示例 Few-shot | 正文「示例」节（1-2 个最小输入输出对，控制 token 预算） |

**标准最佳实践采纳**：可执行脚本优先于长流程描述——六技能各配 `scripts/*.mjs` 薄封装（复用 MCP 工具或 CLI 命令），SKILL.md 正文只保留判断与编排逻辑。

**生态衔接两条**：

- SKILL.md 扩展字段 `capability` 与插件合同 v2 的 `meta.capability` 同词汇表（G1 定词汇表）→ 插件注册即可被技能索引（P3 registry 的发现语义复用）
- 打通 YYC3-CLI 侧既有 `yyc3 skills validate/index/stats` 命令组：技能包落地后由 CLI 校验规范性（含开放规范必填字段校验）——**i18n-Core 出技能、YYC3-CLI 出校验器**，双仓职责延续 file: 单源协作模式

## 八、行业标规对标与自审修正（v1.1.0）

本节为对 v1.0.0 大纲的外部标规审核结论：四路对标（MCP 官方规范 / Agent Skills 开放标准 / 插件生态标规 / 零依赖实现先例），**2 处修正 + 2 处补强**，全部已回灌上文对应章节。

### 8.1 对标结论

| 对标对象 | 权威依据 | v1.0.0 大纲判定 | 修正/补强 |
| ---- | ---- | ---- | ---- |
| MCP 传输规范 | modelcontextprotocol.io 2025-03-26：**Streamable HTTP 取代 HTTP+SSE 双端点**（单端点 POST + 可选 SSE 流式响应）；WebSocket 非官方传输 | ❌ 「SSE+WebSocket 传输矩阵」基于已废弃旧规范 | §4.3 修正为 **Streamable HTTP**（node:http 原生自实现），WebSocket 降为插件层第三方扩展点 |
| Agent Skills 开放标准 | agentskills.io：frontmatter 必填 `name`+`description`（驱动激活匹配）、正文 <5000 tokens、渐进披露三级、脚本优先；兼容 Claude Code/Codex/Cursor/VS Code | ⚠️ SKILL.md 仅写了 YYC³ 标头标尾，缺开放规范必填字段 | §5.3 双 front matter 融合 + 渐进披露纪律 + 提示词六要素写作映射 |
| 插件生态标规 | vite/rollup 官方约定：**插件以工厂函数形态发布**（`createXxxPlugin(options)`），options 闭包配置 | ⚠️ 合同 v2 未显性确立工厂约定 | §八.2 补充：v2 官方推荐形态=工厂函数（内置三插件已是 `createPlugin()` 先例） |
| 零依赖实现先例 | 社区验证：~500 行 node:http 原生 MCP Server（含 OAuth/PKCE）可行 | ⚠️ 「i18n 无依赖」红线未显性声明为实现约束 | §八.3 依赖红线节 |

### 8.2 插件合同 v2 增补：工厂函数约定（对齐 vite/rollup 标规）

```typescript
// 官方推荐形态：工厂函数（options 闭包），对齐 vite/rollup 生态约定
export function createGlossaryPlugin(options: GlossaryOptions = {}) {
  return {
    name: 'glossary',
    version: '1.0.0',
    meta: { capability: ['glossary-lookup'] },   // v2 能力声明
    beforeTranslate(key, params) { /* ... */ },
  } satisfies I18nPluginV2;
}
```

- 裸对象注册仍兼容（v1 遗留可用），但**文档与脚手架一律示范工厂形态**；`@yyc3/i18n-core/plugins` 导出 `definePlugin()` 类型辅助（工厂签名推导 + capability 字面量校验）

### 8.3 依赖红线（项目实况约束的显性化）

| 红线 | 内容 | 依据 |
| ---- | ---- | ---- |
| R-D1 | 运行时依赖恒为零：Streamable HTTP 传输以 `node:http` 原生实现，**禁止引入 express/ws/@modelcontextprotocol/sdk** | 项目「零依赖」核心卖点（README 徽章+竞品差异项）+ 社区 ~500 行零依赖实现先例 |
| R-D2 | devDependencies 可有（vitest/tsup 等），但**不得进入任何 exports 产物**；CI `size-limit` 与 `pnpm audit` 双门守卫 | 现行 CI 七道门禁 |
| R-D3 | 技能包 `scripts/*.mjs` 只允许 import 本包或 node: 内建 | 技能即分发物，随包发布零安装 |

### 8.4 提示词工程要素（技能即提示词）

SKILL.md 本质是分发给 AI 编程工具的**系统提示词**。六要素（角色/上下文/任务/约束/输出格式/示例）已映射至 §5.3 写作模板；另采纳两条社区反模式警示（arXiv SKILL.md 实证研究）：正文**禁止**粘贴大段 JSON 样例（移入 scripts/fixtures）、description **禁止**堆关键词（须为完整触发句，激活匹配依赖语义而非关键词命中）。

### 8.5 审核后度量不变式

§七度量表全部维持；新增两条 G2 收口项：Streamable HTTP 端点通过 MCP 官方 inspector 一致性测试、六技能通过 agentskills 规范校验（`yyc3 skills validate` 扩展规则）。
