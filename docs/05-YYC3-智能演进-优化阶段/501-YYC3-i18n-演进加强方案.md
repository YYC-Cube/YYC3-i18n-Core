## 一、Phase 对账（本方案的事实基线）

以 `docs/INDUSTRY_TREND_ANALYSIS.md`（v2.0，2026-07-12）Phase 0-5 路线图为上游输入，对照 2026-11-04 仓库实况收口：

| 原规划 Phase | 目标 | 实况（2026-11-04） | 对账 |
| ---- | ---- | ---- | ---- |
| Phase 0 开源就绪 | npm 发布 + 文档站 | @yyc3/i18n-core@3.1.0 + i18n-react@0.2.0 已发布 latest；VitePress 10 语言文档站 | ✅ 完成（超额：质量基线 709 测试/覆盖 91.47%+，七道 CI 门禁） |
| Phase 1 React 适配 | React 组件包 | @yyc3/i18n-react@0.2.0（Provider/hook/Trans/next 中间件，21 测试） | ✅ 完成 |
| Phase 2 CLI + CI/CD | CLI 工具链 | `yyc3 i18n init/extract/audit`（YYC3-CLI 单源集成）+ 本仓 CI 七道门禁 | ✅ 完成 |
| Phase 3 MCP 深度整合 | MCP 生态标准 Server | 5 工具 + 仅 Stdio 传输；规划的 12 工具与 SSE/WS 未落地 | ⏳ **本方案主战场（G2）** |
| Phase 4 可视化平台 | Dashboard | 未启动 | 规划（G4 前置） |
| Phase 5 OTA + 企业版 | 热更新 | 未启动 | 规划（G4） |

**结论**：项目已从「库」走完「工具链」，当前站在 Phase 3 门口。本方案将原 Phase 3-5 细化为 **G1→G4 加强路线**，并新增原路线缺失的一层——**技能化（Skill）**。

## 三、插件系统深度分析与 v2 设计

### 3.1 现状（src/lib/plugins.ts，188 行）

合同 `I18nPlugin` 七钩子：`init / destroy / beforeTranslate / afterTranslate / onLocaleChange / onError / onMissingKey`；内置三插件：console-logger、missing-key-reporter（含 autoExport）、performance-tracker（含 slow 阈值与分位统计）。

### 3.2 五项痛点（实查定位）

| # | 痛点 | 证据 | v2 方案 |
| ---- | ---- | ---- | ---- |
| P1 | 钩子**无优先级**——`hookOrder` 即注册序，多插件协作顺序不可控 | plugins.ts:55 `hookOrder: string[]` | `register(plugin, { priority })`，钩子按 priority 稳定排序 |
| P2 | 钩子**类型不对称**——beforeTranslate 返回 `{key,params}｜void`，afterTranslate 返回 `string｜void`，管线语义不一致 | plugins.ts:44-45 | 统一 `PipelineResult<T>`，中间件链签名 `ctx → next()` 化 |
| P3 | **无插件发现机制**——PluginManager 单实例强耦合引擎，无约定目录/懒加载（对比 locale registry 已有 LAZY_LOCALE_REGISTRY 先例） | registry.ts 模式可复制 | `plugins/registry.ts`：`loadPlugin(name)` 懒加载 + 包内 `plugins/` 约定目录 |
| P4 | **单向通信**——onLocaleChange 仅引擎→插件，插件间无事件总线 | plugins.ts:48 | 引擎级 `eventBus`（emit/on），插件可发布 `i18n:report` 类事件 |
| P5 | **内置面薄**——仅日志/缺失上报/性能三项 | plugins/index.ts 39 行 | 新增：cache-warmer（预热高频键）、glossary（术语强制）、tm（翻译记忆）、watcher（键脏检查） |

### 3.3 插件合同 v2（提案骨架）

```typescript
export type I18nPluginV2 = I18nPlugin & {
  priority?: number;                       // P1：默认 100，小者先执行
  meta?: { capability: string[] };         // P3：能力声明（供技能/MCP 发现）
  eventBus?: { emit(topic: string, payload: unknown): void;   // P4
               on(topic: string, h: (p: unknown) => void): () => void };
};
```

向后兼容承诺：v2 为 v1 纯超集，`register(v1Plugin)` 零改动可用（3.1.x 用户无损升级）。

## 四、MCP 现状分析与 G2 扩张设计

### 4.1 现状（src/lib/mcp/，797 行）

工具面 5 个：`search_translations / add_translation_key / translate_key / check_missing_keys / get_locale_stats`；传输仅 `StdioTransport`；仅用 MCP 三原语中的 Tools（Resources/Prompts 未用）。

**文档漂移发现**：趋势文档 Phase 3 节记载的现存 5 工具名（translate_batch/detect_language/validate_icu/audit_coverage/suggest_keys）与实况不符——演进时**以实为准**并回写趋势文档（G1 文档漂移门禁的动机之一）。

### 4.2 G2 工具面扩张（5→12），每一项都是既有模块的协议化

| 新工具 | 复用模块 | 说明 |
| ---- | ---- | ---- |
| extract_keys | cli-integration `extractKeys` 正则逻辑移植 TS | 从代码文本提取 t() 键（MCP 输入=文件内容而非 glob，规避沙箱文件系统暴露） |
| compare_locales | auditCoverage 扁平化逻辑 | 双语言键差异矩阵 |
| quality_score | ai/quality-estimator | 翻译质量评分 |
| auto_fix_icu | icu/parser errors + compiler | ICU 错误定位与安全修复建议 |
| export_formats | 新增 serializer | JSON/YAML/XLIFF/CSV 导出 |
| glossary_lookup | 新增 glossary 模块（G3 插件同源） | 术语强制查询 |
| （升级）report_missing / get_perf | missing-key-reporter / performance-tracker | 内置插件能力 → MCP 工具（G3 三位一体前置） |

### 4.3 传输矩阵与资源面

- **SSE Transport**（远程 MCP，CORS 可配）+ **WebSocket Transport**——使 Claude.ai/Cursor 云端可直接挂载 `@yyc3/i18n-core/mcp`
- **Resources 面**：`locales://{locale}` 只读资源、`coverage://report` 订阅——AI 工具可主动拉取语言包与覆盖率快照
- **结构重构**：i18n-tools.ts 277 行单文件拆为 tool-registry 模式（每工具一文件 + 各自测试），与插件注册表（P3）同构

## 五、插件 × MCP × 技能：三位一体设计（G3 核心）

### 5.1 三层映射

```
能力层（src/lib/plugins/ + ai/ + icu/）      ——运行时扩展点
    ↕ 一比一暴露
协议层（MCP Tools + Resources）              ——AI 工具机器可调用入口
    ↕ 一比一描述
认知层（skills/*/SKILL.md）                  ——AI 编程工具「何时/如何用」的说明书
```

**技能 = 能力的可发现描述 + 可执行入口**；同一实现，三种暴露面，单一事实源（与 YYC3-CLI 的 file: 单源模式同构）。

### 5.2 首批技能矩阵（6 个）

| 技能 | 触发场景 | 执行入口（指向单一事实源） |
| ---- | ---- | ---- |
| i18n-extract | 「给这段代码提取翻译键」 | MCP `extract_keys` 或 `yyc3 i18n extract` |
| i18n-audit | 「检查翻译覆盖率/缺失键」 | MCP `check_missing_keys` + `compare_locales` 或 `yyc3 i18n audit` |
| i18n-translate | 「把 en.json 翻成 ja」 | MCP `translate_key`（AI Provider 直通） |
| i18n-quality | 「评估翻译质量」 | MCP `quality_score` |
| i18n-icu | 「修复这条 ICU 报错」 | MCP `auto_fix_icu` |
| i18n-setup | 「给项目接入 i18n」 | `yyc3 i18n init` |

### 5.3 技能包规范

```
skills/i18n-audit/
└── SKILL.md        # YYC³ 标头标尾 front matter + 触发条件 + 入口命令 + 校验方式
```

- SKILL.md `meta.capability` 与插件 `meta.capability` 同词汇表（G1 定词汇表）→ 插件注册即可被技能索引（P3 registry 的发现语义复用）
- 打通 YYC3-CLI 侧既有 `yyc3 skills validate/index/stats` 命令组：技能包落地后由 CLI 校验规范性——**i18n-Core 出技能、YYC3-CLI 出校验器**，双仓职责延续 file: 单源协作模式

## 六、G4 平台化前瞻（本方案仅定方向）

- **Dashboard（@yyc3/i18n-dashboard）**：消费 performance-tracker/missing-key-reporter 指标流（P4 eventBus 已打通数据面），React 组件库形态复用 i18n-react 底座
- **OTA 热更新**：registry 的 `loader()` 扩展 remote fetch + 版本协商（`locales-registry://` MCP 资源已为此铺路）
- **企业钩子**：审计日志插件化（onTranslate 钩子 v2 新增）+ SSO 翻译工作流

## 七、度量与收口

| 维度 | 现值（2026-11-04） | G2 收口目标 |
| ---- | ---- | ---- |
| 测试/覆盖 | 709 用例 / 分支 91.47%（门禁 90） | 每新工具/插件配测试，门禁不降 |
| MCP 工具 | 5 | 12 |
| 传输 | stdio | stdio + SSE + WS |
| 插件 | 3 内置 | 7 内置 + registry 懒加载 |
| 技能 | 0（仓内）/5（CLI 侧 skills 管理器） | 6 个 i18n 技能包 + CLI 校验打通 |
| npm | core 3.1.0 / react 0.2.0 | G2 末发 3.2.0（合同 v2 + 工具面） |

**执行顺序即风险顺序**：先 G1 冻结合同（避免 G2 扩张期 API 漂移），再 G2 工具面（复用率最高、风险最低），G3 技能（依赖工具名稳定），G4 平台（依赖数据面）。
